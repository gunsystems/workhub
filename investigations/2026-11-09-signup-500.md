오류 시간대(UTC 05:15~05:17)에 생성된 계정 1개, 활성 계정 1개, 이메일 인증 프로필 1개, confirmed OTP 기기 1개, 미확인 OTP 기기 0개. 계정/비밀번호/OTP 초기화나 변경, 별도 인증 세션 생성은 하지 않았다.

## 판단

### 확인된 사실
- 실패 요청은 QR 생성 GET이 아니라 직전 활성화 POST이다. QR 이미지 라이브러리 오류로 단정할 근거가 없다.
- 신규 계정 생성 처리는 이메일 중복·초대 사용 여부를 읽고, 같은 transaction.atomic 안에서 비밀번호 해시를 계산하며 User/AccessProfile/Employee/Invitation을 쓴다.
- 운영 DB는 SQLite, journal_mode=delete, transaction_mode=DEFERRED, busy_timeout=5000ms이다. 웹 요청 외에 주기 실행 스레드도 같은 DB에 기록한다.
- 운영 로그에 HTTP 500 접근 기록은 있지만 상세 traceback/예외명은 찾지 못했다. production DEBUG=False, ADMINS=0이고 현재 django.request에는 별도 stderr handler가 없다. 상위 기본 console handler는 RequireDebugTrue, mail_admins handler는 수신자 없어서 상세 예외가 운영 로그에 남지 않을 수 있는 설정이다.
- 해당 시각은 최근 배포 완료(13:41:27) 이후 약 34분 뒤이며 같은 서비스 instance에서 실패·성공 요청이 처리됐다. 배포 중 화면 전환이었다고 판단할 근거는 없다.

### 유력 가설 — 동시 DB 쓰기 충돌
읽기로 시작한 DEFERRED transaction이 비밀번호 해시 계산 중 유지되고, 그동안 다른 요청/예약 작업이 쓰기 잠금을 얻으면 이후 계정 INSERT가 잠금 승격에 실패할 수 있다. 활성화 view는 IntegrityError만 처리하고 OperationalError는 처리하지 않으므로 이 경로는 500으로 나갈 수 있다. 재시도 성공 양상과 일치한다.

별도 임시 SQLite DB에서 reader의 BEGIN/SELECT 뒤 다른 connection이 쓰기 잠금을 가진 상태를 만들어 같은 메커니즘을 재현했다. 첫 INSERT는 즉시 `database is locked`, transaction 종료 후 재시도는 성공했다. **이것은 가설의 가능성 검증이며 당시 운영 예외가 동일했음을 증명한 것은 아니다.** 재현은 운영 DB를 열거나 변경하지 않았고 프로그램은 .tmp/analyze_signup_lock.py에 있다.

## 권장 보완 (미적용)

1. production에서 상세 예외명·실패 단계·요청 식별자를 stderr에 남기되 비밀번호/OTP/코드/토큰/초대 URL은 마스킹한다. DEBUG를 켜서 사용자에게 traceback을 노출하는 방식은 쓰지 않는다.
2. 비밀번호 해시 계산을 DB write transaction 밖으로 이동해 읽기/쓰기 잠금 보유 시간을 줄인다.
3. 계정 생성 DB 묶음의 잠금 오류만 새 transaction에서 제한 재시도한다. 각 시도마다 초대 토큰/만료/이메일 인증 세션/직원 사용 여부/중복 계정을 재검사하고, 중간 실패는 모두 rollback해야 한다.
4. 지속적인 잠금은 일반 500 대신 안전한 재시도 안내로 처리한다. 성공 후 중복 생성이나 초대 재사용을 허용하지 않는다.
5. 전역 SQLite IMMEDIATE/대기 시간 또는 PostgreSQL 전환은 별도 동시성·처리시간 검증 후 결정한다. timeout만 늘리면 해결된다고 가정하지 않는다.

위 항목은 분석 결과와 제안이며 적용 완료 기록이 아니다. 이미 완료한 계정의 재등록/OTP 초기화는 이번 분석 결과상 필요하지 않다.
